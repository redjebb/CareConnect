# CareConnect – документация на проекта

**Направление:** Софтуерни приложения · **Автори:** Адам Биков, Реджеб Туджар
**Онлайн:** https://careconnect-d7bd7.web.app · **Код:** https://github.com/redjebb/CareConnect

## 1. Проблем и цел
Домашният социален патронаж доставя топла храна на възрастни и самотни хора. Днес координацията често е на хартия и по телефон: няма проверка дали храната е стигнала, подписите се губят, а при проблем (човекът не отваря) никой не научава навреме.

**Цел:** дигитална платформа, в която диспечерът планира маршрутите, шофьорът ги изпълнява на телефона си (дори без интернет), клиентът се подписва дигитално, а при проблем диспечерът получава SOS имейл веднага.

**Какво е различното:** постоянни бележки за достъп към всеки клиент („3-ти етаж, вратата вдясно“), които се показват на шофьора при всяко посещение и се обновяват от него; автоматично пренареждане на маршрута; работа офлайн; аналитика и откриване на пропуснати посещения.

## 2. Потребители и роли
| Роля | Какво може |
|---|---|
| Системен администратор (MASTER_ADMIN) | Всичко + добавя и премахва мениджъри |
| Оперативен мениджър (MANAGER) | Регистър на клиенти, дневен график, шофьори, отчети, аналитика |
| Шофьор (DRIVER) | Вижда само своите посещения; подпис, check-in, SOS, бележка за достъп, смяна |

## 3. Функционалности
1. **Регистър на клиентите** с ЕГН, адрес (подсказки от ArcGIS), телефон, ястие и **постоянна бележка за достъп**.
2. **Дневен график** – клиент към шофьор и дата; бележката се копира автоматично.
3. **Шофьорско приложение (PWA)** – карта (Leaflet), навигация (Google Maps/Waze), оптимизиран маршрут, смяна с начало/край и обобщение.
4. **Дигитален подпис** на шофьор и клиент (Canvas) при доставка.
5. **SOS / проблем** – записва се инцидент и се изпраща имейл до диспечера, планирал посещението.
6. **Офлайн режим** – промените се записват локално и се синхронизират автоматично; интерфейсът показва колко промени чакат.
7. **Оптимизация на маршрута** – алгоритъм „най-близък съсед“ + 2-opt от текущата позиция на шофьора.
8. **Аналитика** – доставки по дни, успеваемост, ефективност на шофьорите, най-чести проблеми, пропуснати посещения.
9. **Отчети** – месечен отчет (PDF/печат) по клиент и общ.
10. **Покани по имейл** с еднократен токен за активиране на акаунти.
11. **GDPR:** експорт на всички данни за човек (JSON) и пълно изтриване („право да бъдеш забравен“) от профила му.
12. **Демо режим без интернет и без риск за реалните данни:** `npm run demo` стартира локални емулатори с примерни данни и акаунти за всяка роля.

## 4. Архитектура
```
React + TypeScript (Vite, PWA)            Firebase
┌───────────────────────────────┐    ┌──────────────────────────┐
│ views/        екрани           │    │ Authentication            │
│ components/   UI компоненти    │───▶│ Cloud Firestore + Rules   │
│ hooks/        състояние        │    │ Hosting                   │
│ services/     достъп до данни  │    └──────────────────────────┘
│ utils/        чиста логика     │    ArcGIS (геокодиране) · EmailJS (имейли)
└───────────────────────────────┘
```
- **Разделяне на слоевете:** екраните не говорят директно с базата – минават през `services/`; алгоритмите (разстояние, маршрут, статистика, валидация, офлайн) са чисти функции в `utils/` и са покрити с тестове.
- **Данни (Firestore):** `users`, `admins`, `drivers`, `clients_registry`, `clients` (по един документ на посещение), `schedule`, `shifts`, `deliveryHistory`, `incidents`, `invitations`.
- **Производителност:** страниците на ролите се зареждат лениво (code-splitting), а Firebase, картите и PDF са в отделни пакети; адресите, вече намерени от ArcGIS, се кешират на устройството, така че картата работи и офлайн. `ErrorBoundary` показва екран за възстановяване вместо празна страница.
- **PWA:** манифест, иконки и service worker – инсталира се на телефона и зарежда приложението и без връзка; Firestore пази данните в локален кеш.

## 5. Сигурност
- Авторизацията се определя от профил `users/{uid}`, достъпен само за четене от собственика; ролите не могат да се самоприсвояват.
- **Принцип на най-малките права (Firestore Rules):** шофьорът чете само клиентите, графика, смените и сигналите, свързани с него; регистърът с ЕГН е достъпен само за персонала; всичко непосочено е забранено.
- **Покани с токен:** активирането изисква случаен еднократен токен, получен по имейл; токенът не може да се прочете от поканения.
- Валидация на входа (ЕГН, телефон, имейл, дължина на бележките), без лични данни в конзолата, парола минимум 8 символа.
- 25 автоматични теста проверяват правилата срещу емулатор на Firestore (опити за подправен токен, ескалация на роля, достъп до чужд клиент и др.).

## 7. Инсталация и стартиране
```bash
npm install
npm run dev        # http://localhost:5173
npm test
npm run build
```
Изисква Node.js 18+. За `npm run test:rules`, `npm run test:e2e` и `npm run demo` е нужна и Java 21.

**Демо режим:** `npm run demo` → http://localhost:5173, акаунти `master@demo.bg`, `manager@demo.bg`, `driver@demo.bg`, `driver2@demo.bg` (парола `Demo12345!`; съществуват само в локалния емулатор). Подходящ резервен вариант при проблем с мрежата по време на защитата. Публикуване: `docs/SECURITY-AND-DEPLOY.md`.

## 8. Потребителско ръководство
**Диспечер:** 1) „Клиенти → Регистър“ – добавете човек и постоянна бележка за достъп. 2) „Дневен график“ – изберете човек от регистъра, шофьор и дата; бележката се попълва сама. 3) „Аналитика“ – следете успеваемостта и пропуснатите посещения.

**Шофьор:** 1) Влезте и натиснете „Започни смяна“. 2) Следвайте подредения маршрут; прочетете синята бележка „Достъп“. 3) „Доставено“ → подписи на шофьор и клиент. 4) При проблем – „Проблем / SOS“. 5) Ако бележката е неточна, „Промени бележката“ – ще се покаже и при следващите посещения. 6) Без връзка продължавайте нормално – лентата горе показва, че промените ще се синхронизират.

## 9. Бъдещо развитие
